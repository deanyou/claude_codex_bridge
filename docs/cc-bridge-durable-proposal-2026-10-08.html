00分析结论（先说清楚）

① 你说的“PaLM Durable”不存在——Google 没有这个产品。实为 Pi 的 pi-durable（@earendil-works/pi-durable，与 Pi 1.0 同期发布的 experimental 包，本文以 1.1.0 为评审基线）：状态提交后才展示；使用 SQLite 时可恢复已提交的会话与任务。工具副作用是否可重放需单独定义，不能由“durable”推导出恰好执行一次。

② CC Bridge 的 pi provider 后端现状：起的是 Pi CLI（tmux pane），走 native session resume + 自研 completion 扩展。没有接 pi-durable 的 SQLite 存储。→ 这就是接入点。注：扩展文件名 cc_bridge-pi-completion.ts 不在仓库 tree 里——源码内嵌于 launcher.py（_PI_COMPLETION_EXTENSION_SOURCE），启动时写盘再 --extension 传给 Pi CLI。

③ codex provider 已有。mailbox_kernel + message_bureau 的 A→B→C 路由已有。注：pi.inbox 是 pi-durable 官方 README 列出的内置文档（queued submissions），入队 API 为 root.submit()——两者并存。

④ Python↔Node 边界：新增常驻 Node 桥，经 TCP loopback JSON-RPC 连接 Python provider backend；桥独占 durable storage。协议见 09 节。

⑤ 当前 mailbox 不是 SQLite：MailboxStore / DeliveryLeaseStore 使用 JSON，InboundEventStore 和 message bureau 使用 JSONL。事件、lease、摘要分别写入，没有跨文件事务。

范围：本文是接入提案。标为“新增”的绑定账本、派发幂等、独占锁、对账和验收均待实现；现有 provider 与路由不代表这些保障已经具备。动图只演示目标行为。

01一句话方案

CC Bridge 做 tmux 编排与 mailbox 路由；Pi Durable 做 supervisor 的持久记忆与断点续跑；Codex 做执行。三层各管一层，合起来是一条“挂了能续、结果可审计”的多 agent 回路。

04正常回路

  1. 持久记录输入意图 → mailbox 保存输入事件；独立绑定账本先记录规范化 storage 路径、conversation 身份、inbound_event_id、requestId 与输入摘要，再调用桥。
  2. durable 接受输入 → 桥调用 root.submit()，daemon 持久记录返回的 submission_id。回包丢失时用同一 conversation 与 requestId 重试以取回原 submission，不生成新 ID。
  3. supervisor 拆分与派发 → 派发工具先在 durable 状态中记录子任务键；经 daemon 幂等派发接口进入现有 mailbox。工具重放查询或返回同一 job / attempt，不另建任务。
  4. worker 执行上报 → 结果带 attempt_id、稳定 result_id 与证据摘要写入结果记录。未知副作用必须核查；completion 不是副作用提交凭证。
  5. Verifier 门禁 → 检查对应 attempt 的 diff / 测试，持久记录验收结论；返工创建明确的新 attempt，保留原任务及结果关联。
  6. 最终结论与交付 → durable submission 终态和答案先提交；daemon 按稳定 result_id 写回 mailbox，再记录交付确认。会话 provider 身份保持以支持缓存亲和，但不保证服务端 prompt cache 永不失效。

05崩溃恢复与幂等边界

场景 A · worker 崩溃

确认 pane / worker 状态后，核对 message、attempt、结果及副作用证据。已提交结果直接复用；允许重试的任务按策略恢复或创建新 attempt。文件或外部 API 已变更而结果未提交时，状态为“副作用未知”，阻塞核查或执行任务专属补偿，不能盲目重派。

键的职责：logical_task_id 标识逻辑任务；attempt_id 标识一次执行；dispatch_key 在同一次派发的 RPC 重试及 durable 工具重放中保持不变；effect_id 在同一副作用的重试中保持不变。新 attempt 不能自动被视为副作用安全。

工具重放：replay: "safe" 允许 crash 后重新调用 execute()，不是只重放已存结果。派发工具只有在 daemon 按 dispatch_key 查询 / 复用既有记录、重复调用不重复产生效果后才能声明 safe。未声明安全的中断工具按 interrupted 处理。官方工具语义

承诺边界：输入去重、派发幂等和结果交付幂等分别验收。任意 worker 的文件写入或外部操作不承诺“恰好执行一次”；自动重试只适用于已定义幂等 / 补偿协议的任务。

场景 B · supervisor / 桥失联

心跳超时仅标记“疑似失联”并停止新投递。核实旧桥身份，发送 SIGTERM（Windows 使用对应进程控制），等待并确认退出；必要时按超时策略强制终止。旧桥未退出或独占锁仍被占用时 fail-closed，不启动第二个 storage owner。

接管顺序：确认旧桥退出 → 新桥取得规范化 storage 路径的 OS 独占锁 → 安装同版本 registry / extensions → Harness.open() → 重新绑定 conversation 与 submission → 对账 → 启动 resume() / 恢复等待和投递。submit / wait 本身也会启动调度，因此对账前不得调用它们启动新工作；确需重放 submit 才能取回 submission_id 时，应先完成该输入的投递资格核对，再以原 requestId 调用，并继续对账。

claim() 的事件 append、lease save、摘要更新是分离写入。故障注入必须覆盖任意相邻写入之间：事件为 DELIVERING 但 lease 缺失，或事件 / lease 已更新但摘要过旧，都先对账再决策。现有 JSONL append 未提供跨文件事务；新增账本须明确 flush / fsync、尾部损坏处理及确认返回条件。

跨存储绑定与对账协议（新增）

daemon 维护独立、可重建查询索引的持久绑定账本，以输入事件及目标 conversation 为键。记录 inbound_event_id / message_id / attempt_id / requestId / input_hash / storage_path / conversation_id / submission_id / result_id / delivery_phase；明确 conversation ID 与 provider 缓存 UUID 的区别。提交 RPC 前先持久记录输入意图；submission_id 返回后补记绑定；同一 requestId 的输入摘要不一致时拒绝。

DeliveryLease 可保存 submission_id 作为运行期引用，但不能作为唯一映射来源：当前终态转换会释放并删除匹配 lease。映射和结果交付确认必须在 lease 删除后仍可查询；schema 迁移和旧记录缺字段的处理列为实现工作。

故障窗口恢复动作禁止推断
durable 已接受输入，submit RPC 回包丢失根据已记录的输入意图，在原 storage / conversation 上重放相同 requestId 和输入，取回原 submission_id；持久补记绑定不能因缺少 submission_id 就新建请求
durable 答案已提交，mailbox 结果尚未记录通过桥查询指定 submission 终态和答案，按稳定 result_id 补交并记录确认不能因 mailbox 仍 pending / delivering 就重新执行已完成输入
结果写入或 ack_reply() 成功，RPC 回包丢失查询 result_id 的持久记录及 inbound_event_id 的终态，重复确认返回已记录结果；必要时重建摘要ack_reply() 只确认 mailbox 回复消费，不会使 durable submission 完成
mailbox 与 durable 状态冲突或缺乏证据分别尊重各自权威：durable 的 run / submission，mailbox 的投递 / 消费；依据绑定和交付记录对账，无法判定时阻塞并报告resume() 不覆盖 mailbox 状态，也不能以任一存储直接替代另一方

07验证清单（v4）

基础冒烟

  • kill worker pane → 已提交结果复用；可安全重试任务恢复；副作用未知任务阻塞核查，未确认前不盲目重派
  • kill supervisor / 桥 → 完成独占接管与对账后 resume()，conversation 及 provider 会话身份保持
  • Verifier 拦截 → 验收结论持久化，返工使用新 attempt，原结果与最终汇总保持可追溯
  • Python client → 起桥 → submit → 杀桥 → 重启 / 重连 / 重新 open → 查询原 submission 并恢复

幂等保障与三个故障窗口

  • 派发成功后丢回包：daemon 已持久接受 dispatch_key，DELIVERING 事件已写，RPC 回包丢失 → durable 工具重放 / 重启查询返回原 job / attempt，不新建重复派发；同一 requestId 的输入重放也返回原 submission
  • 答案提交后丢回执：durable 答案已提交而 mailbox 未写 → 按 result_id 补交；mailbox 结果或 ack_reply() 已写但确认回包丢失 → 查询已提交记录，确认幂等。两种窗口分别注入
  • 旧桥失联但仍存活：停心跳但保留进程 / 锁 → 停投递 → 终止并确认退出 → 新桥取锁。旧桥拒绝退出时新桥不得打开 storage
  • 工具 execute() 派发成功、durable 工具结果未提交即 crash → safe 工具重放复用同一 dispatch_key；未声明 safe 的工具得到 interrupted
  • worker 写文件 / 调用外部接口后、结果提交前 crash → effect_id 去重或任务专属核查生效；缺少协议时进入阻塞态

存储一致性

  • 分别在事件 append → lease save → 摘要更新之间 crash；恢复后摘要 / lease / 事件与绑定账本对账，决策不依赖单边状态
  • lease 带 submission_id 的引用（如启用）可恢复；终态删除 lease 后，独立账本仍能查到原 submission 与交付确认
  • JSONL 尾部半行 / 损坏记录按规定隔离并报告，不被解释为“尚未投递”而触发重复派发
  • 规范化路径 / 符号链接别名、两个 daemon 争用同一 storage、daemon 重启遗留桥均只能产生一个 storage owner

completion 与传输

  • 按 09 节映射表验收 stop + reply、error、空 reply、缺 outcome、其他终态；中间工具调用、排队、跨 request 输入和过期 bridge_epoch 不得误判完成
  • TCP loopback 随机端口发现、token 认证、过期 endpoint、指数退避及重试预算耗尽后的 fail-closed 生效
  • 桥重启后 client 取得新 epoch / handle，原 storage / conversation / submission 绑定保持；旧 handle 不能继续操作

08风险与保障范围

experimental API。本文以 pi-durable 1.1.0 为评审基线；实施时选定并锁定确切版本及依赖。升级需通过桥协议、存储及 completion conformance，并定义迁移 / 回滚兼容性；不依赖内部 API。
持久化不等于副作用恰好一次。requestId 去重限于指定 conversation 的 submission；文件 / 外部 API 效果需要独立幂等或补偿协议。故障恢复目标是可核对、可重试或明确阻塞。
持久化不等于质量合格。completion 判断输入是否得到终态答复；Verifier 根据验收标准裁决质量。不能用 completion 直接替代验收。
状态权威有边界。durable store 管 run / submission；mailbox / message bureau 管投递 / 结果消费；绑定账本连接两者。durable 模式的 pane 日志只展示，不能在失联后提升为完成判定来源。
故障模型。优先验收进程崩溃。官方 SQLite 默认 WAL + synchronous=NORMAL，不能据此保证掉电 / 主机故障时最后一次提交不丢；现有 CC Bridge JSONL append 也不是 fsync 提交。若需主机故障保障，应另行指定存储刷新策略并验收。官方存储说明

09Node 桥与 completion 协议（v4）

形态：常驻 Node 桥随 daemon 起停；统一 127.0.0.1 TCP loopback 上的 JSON-RPC 2.0，Python provider backend 保留 thin client。durable 模式的 pane 是状态展示客户端，不另开拥有同一 storage 的 Pi CLI。

CC Bridge daemon ├─ 持久绑定账本 / 派发去重 / 结果确认 / 对账 ├─ Node 桥（常驻；取得 OS 独占锁后 open storage） │ JSON-RPC 2.0 over 127.0.0.1 TCP · token · bridge_epoch │ open(storage_path, conversation_id?) → handle + conversation_id │ submit(handle, input, requestId) → submission_id │ status / wait(handle, submission_id) · resume(handle) │ read_inbox / read_transcript（均经桥查询） └─ Python thin client launcher: 启动 / 绑定桥，pane 展示已提交状态 execution: 先记意图 → submit → 持久补记绑定 completion: 查询指定 submission，映射终态 → 幂等交付

上列为拟新增桥 RPC；不是 pi-durable 的直接 API 签名。handle 仅在某一 bridge_epoch 内有效，不能代替持久 storage / conversation / submission 身份。

端口、认证与重连

端口发现：桥绑定 127.0.0.1:0 获取随机端口；完成初始化后原子发布项目运行目录中的 endpoint.json，包含 host、port、PID、bridge_epoch、protocol_version 和随机 token。POSIX 文件权限 0600；Windows 使用仅当前用户可读写的 ACL。启动和接管校验进程身份及 epoch，不仅看 PID / 文件是否存在；退出仅清理自己 epoch 的 endpoint。

协议：UTF-8、每行一个 JSON-RPC 消息，设置消息长度上限；每次请求携带 token 和 bridge_epoch，鉴权失败拒绝处理。token 不写普通日志。RPC id 只关联传输回包；requestId / dispatch_key 才是业务去重键。协议版本不兼容时 fail-closed。

重连：从 250 ms 开始指数退避，间隔上限 5 s，加入抖动；每轮重连总预算 30 s，耗尽后保留待对账记录并报错。重试前重读 endpoint；重连认证后重新 open 原 storage / conversation，取得新 handle，并查询原 submission。对可能已产生效果的 RPC 先查询或使用原业务幂等键重试，禁止换键盲重发。

storage 独占与降级

桥在规范化 storage 路径对应的固定旁路锁文件上取得 OS 独占锁（POSIX fcntl.flock / Windows LockFileEx），从打开 storage 前持有至关闭后；进程内同时禁止重复打开同一 storage。锁文件在接管中不删除重建，避免旧、新 owner 锁住不同文件。Python 只管理桥和账本，不直开同一 durable SQLite。新桥取锁失败即阻塞，不能依靠 SQLite 自身写锁代替 harness ownership。官方单进程约束

fail-closed：桥失联、对账冲突、旧桥身份不明、锁未释放或协议不兼容时阻塞并报告。durable 模式不 fallback 到 pane 日志判完成；如需改用现有 pane 模式，先终结或隔离原 durable attempt，再由显式策略创建新 attempt，不继承未确认的完成状态。

completion 状态映射

当前 pane backend 绑定 request_anchor / runtime instance，读取结构化事件，以 agent_settled 为终态触发；不是正则判断 AssistantEntry。适配器将 terminal_authority 写入 runtime state（默认 pi_extension_agent_settled），并在终态诊断中输出；它是来源标签，不能替代事件和绑定校验。

durable backend 必须先确认指定 submission 已进入终态，再读取关联答案的 outcome / reply；不能只因出现 AssistantEntry 就判完成。用桥的 conformance 固定确切版本的 submission / answer 字段及错误原因映射，并记录独立来源标签 pi_durable_submission_terminal、submission_id 与 bridge_epoch。
